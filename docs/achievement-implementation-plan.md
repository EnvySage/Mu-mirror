## 共用实现约定

1. 继续使用 PostgreSQL 事务事件队列、共享指标与 JSON 规则目录；每枚章维护元数据和规则，不逐章新增 service/controller/计数表。已有指标复用 gte/all/any；确有新规则形态才扩展规则词汇。
2. code 是稳定身份；已有获得记录永久保留。第一批不改变原 34 个定义，名称/口径差异在后续迁移时逐项审核，不覆盖既有授予。规则语义改变时递增 ruleVersion。
3. 服务端负责业务成功事实、归属和去重；客户端只报告可验证的查看动作。按业务对象、日期、会话等显式选择去重粒度，不能把已有永久去重事件拿来统计跨天行为。
4. 所有日期在 Asia/Shanghai 聚合，自然周按周一开始；不同月份包含年份。不同日期不等于连续日期，同一年四季度不能拼接多个年份。
5. 只有已实现并验证的定义进入正式账号目录；未实现条目留在 96 枚前端设计预览。通过 scripts/sync-achievements.py 同步生成账号展示副本。
6. 每批核查是否需要 DDL，数据库结构变化必须新增迁移并更新新库基线；不改写已发布迁移。无 DDL 的批次也记录发布顺序和核对方式。
7. 基于隔离 PostgreSQL 测试补发、边界、归属、重复消费与进度；前端同步后跑测试和构建，实际账号界面检查。

## 第四批：24 项镀层与发布收口

- 把镀层作为同一 code 的进阶授予，独立记录 platedAt/规则版本/通知确认；普通章和展示位数量不变。数据库变更单独迁移。
- 完整挑战条件仅保存在服务端；未镀层时 API 只暴露可镀层，不返回隐藏规则、目标或进度。原章未获得时满足更高条件，应正确授予原章与镀层。
- 复用前几批的日期、集合、关联与顺序指标，实现目录文档中全部 24 项挑战；普通与镀层可共用事实，不能复制 24 套业务流程。
- 前端真实账号接入镀层状态与通知、原章/镀层比较、8/10 位展示架。预览外观不能写入账号状态。
- 旧数据仅按可证明事实补发；缺失查看或关联历史不猜测。验证重复迁移、规则升级、并发核对、撤删来源后保留授予、展示架版本冲突、性能与完整回归。
