# 镜子归档与累计链路修复设计

**状态：待评审**

**日期：2026-10-17**

## 目标

镜子是用户在生成时认可输入数据后形成的历史归档。之后软删除原始记录，不应让已生成镜子从历史中消失；软删除记录也必须从后续镜子的原始输入中排除。月度镜子继续利用先前镜子保持累计叙事，但删除、修改或撤权不能经由旧镜子把受影响内容带入未来镜子。正常生成新一期时不重算全部历史。

## 当前行为与问题

- 月度镜子将上一期镜子、回看窗口内的原始记录、校正索引和实时统计作为生成输入。递归链是刻意设计的累计语义，见 `MirrorServiceImpl.buildRequest` / `buildPrevMirror`。
- 原记录采用软删除，镜子统计 SQL 以 `records.deleted_at IS NULL` 排除它，因此新的原始输入不会直接读取已删除记录。
- 软删除、记忆授权变化会调用 `invalidateForUser`，一次将用户全部快照标为失效。AI 生成链排除失效快照是合理的保护；但历史列表也过滤 `invalidated = false`，导致已生成的归档无法查看。
- `ProfileSnapshot` 注释已说明失效镜子应保留展示、只退出后续 AI 推断；查询实现与该语义相反。
- 同月重生成会先删除该月份旧快照再插入新快照；清理逻辑还会删除超过现有保留数量的快照，均与长期归档语义冲突。
- 快照当前没有保存原始记录、片段或父快照的依赖清单，无法准确找出某条记录影响了哪些镜子。

## 产品规则

1. **归档可见性与生成资格分开。** 所有快照默认只读、归档且对所属用户可见。`invalidated` 表示“不可作为后续生成上下文”，不表示删除或隐藏。
2. **源记录后续删除不回写历史。** 软删除只设置 `deleted_at`。历史镜子保持生成时的内容。若镜子提供来源记录链接，来源行仍存在时显示“原记录已删除”，不返回其正文。
3. **未来生成排除当前不可用的源。** 新镜子使用生成时仍有效且获授权的记录与片段；被软删除、撤销记忆授权或物理清除的来源不得作为新的原始输入。
4. **旧镜子不能绕过源授权。** 月度镜子会引用先前镜子，因此修改、删除或撤权后，直接依赖受影响来源的快照及其后代快照应退出 AI 上下文；它们仍保留为归档。
5. **普通生成只增量生成目标期。** 没有受影响祖先时，只生成一份新快照，使用最近的安全基线与目标期数据，不重跑历史月份。
6. **历史修正延迟到下次生成。** 数据变更时只标记受影响的依赖链，不立即调用 LLM。下次请求生成时，从最早受影响期之前的最近安全检查点开始，按月重放到目标期；未受影响的月份不重算。只有发生影响历史链的修改、删除或撤权时才会多次生成；普通新月生成仍只生成目标期一次。
7. **重新生成保留旧版本。** 同一月份重新生成应新增版本，旧版本继续作为归档。只有用户显式删除镜子或删除整个账户时才清除归档。

## 数据模型与接口

### 快照状态和版本

- 保留现有 `invalidated` 的 AI 上下文含义，API 增加清晰的状态与原因字段（例如 `context_status`、`invalidated_at`、`invalidated_reason`），供时间线显示“可用于生成”或“仅归档”。
- 月度快照增加版本号与当前版本标记；调整当前的 `(user_id, period_month)` 唯一索引，使同月可保留多个版本，但至多一个当前版本。手动快照本身就是独立版本。
- 停止因普通失效或同月重生成物理删除快照。历史列表改为分页读取所有归档，避免当前 14 条上限导致较早镜子再次“消失”。

### 依赖溯源

新增快照输入依赖表，至少记录：

- 快照实际引用的父快照 ID（包括递归 prompt 中传入的旧月摘要）；
- 直接进入统计、回看原文或校正索引的 record/chunk ID；
- 依赖类型，便于解释某份镜子为何变成“仅归档”。

生成器组装输入时同时收集这些 ID；记录依赖必须覆盖原文回看和统计事实所涵盖的记录，父快照依赖必须覆盖 prompt 中传入的前期全文与旧期摘要，并在快照写入事务内保存。来源软删除后，保留 record/chunk 行及 ID，以便历史详情能够显示删除标记。若以后执行物理清除，则依赖表只保留不可逆的来源 ID/删除时间墓碑，不保留原文。

### 影响范围计算与懒重放

- 新建、无关月份的数据追加不使历史归档失效；新期生成时自然把新增数据作为增量。
- 编辑已获授权片段、撤销片段授权、软删除记录时，根据来源依赖找出直接快照，再沿快照输入依赖向后标记所有后代为“仅归档”。
- 目标月份生成时，若其上下文链含“仅归档”祖先，选择最早受影响期前最近的安全快照为检查点，重建受影响期到目标期的月度版本。中间期是否重放以该期之前存在可见快照且能参与后续累计链为准。
- 若受影响链之前没有安全检查点（例如旧快照尚无依赖追踪），从最早可用的未删除、已授权原始数据月份开始建立新链；无法覆盖的历史段明确显示为归档断点，不把它伪装成完整累计镜子。
- 镜子生成与来源删除/撤权共享用户级事务锁，避免来源变化发生在 AI 请求期间、却漏掉尚未落库镜子的竞态。
- 保守失效旧版未追踪快照时，包含已被新版本替代、但仍可能被后代引用的非当前祖先。
- 无安全检查点时，重放同时纳入归档里缺失、但仍有已授权记录的月份；只要最早仍授权来源晚于最早历史镜子，就给新链写入 `archive_discontinuity=true`。后续月度镜子和手动镜子沿父依赖继承此标记。
- 不在删除/撤权请求中同步重算，也不在每次正常月度生成时重算全史。
- 旧快照没有依赖数据，迁移后标记为“来源未追踪”。它们保留展示；不得仅因迁移就清空其内容。涉及旧数据的变更在无法精确定位时，对旧的上下文链采用保守失效，等新版本建立完整依赖后恢复精确传播。

## 前端行为

- 时间线显示所有归档，包括当前可用于后续生成的镜子和“仅归档”镜子；展示生成时间、归属月份、版本及失效原因。
- 时间线和镜子正文明确显示 `archive_discontinuity`，说明累计历史有一段无法从当前授权来源重建。
- 月度镜子以 `period_month` 作为归属月份，`created_at` 仅表示生成时间。
- 重新生成月份时提示会创建新版本、保留旧版本；不能用“删除旧快照再插入”实现。
- 可生成月份从有效记录覆盖月份及已有月度镜子的 `period_month` 推导，包含仅归档的月份；空状态文案描述真实情况，不再以“近两个月都有镜子”代替“没有可生成月份”。
- 来源链接目标若已软删除，显示墓碑状态，不尝试载入正文。

## 迁移与兼容

- 数据库迁移只增加版本、状态原因、依赖关系所需结构，并调整月度唯一索引；已有快照正文、向量和状态不清空。
- 已存在快照统一作为版本 1。已有 `invalidated = true` 的记录展示为“仅归档”；不自动重新授权其 AI 上下文。
- `GET /mirror/snapshots` 的轻量列表增加归属月份、版本和上下文状态；详情 API 可读取失效但仍归档的快照。用于聊天推断的查询继续只选择当前、上下文有效的快照。
- 迁移本地验证通过后再单独讨论生产数据库部署；本设计不授权生产库写入或服务部署。

## 验收标准

1. 软删除来源记录后，原快照仍在时间线和详情中；来源若可追溯，则显示“原记录已删除”。
2. 后续新镜子的原始统计与文本输入不包含该软删除记录。
3. 受影响的旧镜子不再被递归累计链引用，但仍可供用户查看。
4. 不受影响的快照仍可作为安全基线；普通新月生成只新增目标期（一次镜子生成调用），不触发历史 LLM 重算。
5. 删除较早来源后，下次生成从最早受影响月份的安全检查点重放；重放旧月份产生新版本并保留旧归档。
6. 同月重生成不删除已有版本；月度归属按 `period_month` 显示。
7. 历史列表包含失效归档且分页稳定；聊天/推断只读取上下文有效快照。
8. 数据库迁移可在空库与现有含失效快照的数据库上重复验证，不丢弃已有快照正文。
