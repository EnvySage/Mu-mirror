## 产品哲学（讨论中确立的锚点）

- 镜子不是通用助手，是**拿着你的证据和你对话的镜子**
- RAG 管"那件事怎么样了"，工具管"这段时间整体怎么样"、"该记住什么"、"该做什么"
- 有存有取，对话才像一个"有记忆的实体"而不是问答机
- 只读工具先行是旧思路；**vault 加入后，写操作红线 = 显式动作免确认、对话内写操作必须确认**

## A. 基础工具层（地基，全只读）

### A1. search_records 按条件查记录
- 维度：关键词/日期段/情绪/contentType
- 价值：RAG 是相似度召回，精确条件查询是盲区（"上个月带'论文'的记录"）

### A2. get_stats 周期统计
- 复用已建 stats mapper（频率/情绪分布/待办剩余），零新 SQL
- 价值："我这月写了几篇"——RAG 拿问题算向量相似度纯浪费，工具直接聚合

### A3. get_profile 最新画像
- 五维数据 + 上次快照时间
- 价值："我最近状态怎么样"直接给结构化数据

### A4. get_glossary 词典查询
- 价值："论文是指什么来着"——查用户个人词典

### A5. compare_snapshots 快照对比
- 数据已有（快照历史+对比接口都做了）
- 价值："上个月的我和这个月的我差别大吗"——把镜子页图表能力搬进对话

## B. 创新场景层（只有这个架构做得好的）

### B1. 事实核查镜子 verify_claim ★★★（候选论文核心卖点）
- 场景：用户说"我这周啥也没干摆烂了"→ 镜子检索本周记录，拿证据温和纠正："真的吗？你周三写了检索实验笔记，周四调了 embedding"
- 机制：LLM 先判断陈述是否为可核查的自我评价 → 是则先检索再回答
- 学术锚点：行为激活疗法的事实核查；焦虑/抑郁用户的系统性负性偏差用本人记录纠正
- 成本：中。复用四路检索 + "核查模式" prompt
- 论文叙事：**记忆接地的自我核查对话**（memory-grounded self-verification）

### B2. 认知边界透明 coverage_check ★★★（可信 AI）
- 场景："我 RAG 实验什么时候开始的？"→ 镜子答前先查覆盖度："你 8 月 12 日前的记录里完全没提 RAG，之后有 14 条——大概 8 月中旬开始。**8 月之前我对你这部分一无所知，因为那时候你还没开始写**"
- 机制：回答前先查"我知道多少、从哪天开始知道"，声明知识边界
- 学术锚点：epistemic humility（认知谦逊），AI 可信度研究方向
- 独特性：通用 LLM 假装全知；**"洞"（没写的日子=不存在）只有记忆库架构才有**
- 成本：低

### B3. 对话中即时教镜子 in-dialogue lexicon teaching ★★
- 场景：对话里纠正"不是这篇论文，是我导师那篇"→ 镜子："要我把「论文」拆成两个词条吗？①毕业设计论文 ②导师课题论文 [确认/不用]"
- 机制：对话即词典维护入口，纠正瞬间转 pending 词条走已有 confirm 审核流
- 独特性：**用户模型在对话中被即时编辑**（in-situ model editing）
- 依赖：词典 sprint 上线后接，成本低

### B4. 和过去的自己对谈 snapshot persona ★★（演示效果最佳）
- 场景："用 8 月的我回答：那时候最焦虑的是什么？"——上月画像快照作为 persona 注入，LLM 以"8 月的你"口吻回答；进阶：同一问题让 8 月的你和现在的你各答一遍，对比差异
- 依赖：快照时间序列（已做完）
- 成本：低，纯 prompt 工程
- 演示价值：答辩现场效果炸裂

### B5. 词典漂移澄清 proactive disambiguation ★★
- 场景：问"我游戏打得咋样"，而"游戏"有漂移历史（3 月=明日方舟，8 月起=FGO）→ 镜子不猜，反问："你说的是最近的 FGO 还是 3 月那个明日方舟？"
- 机制：漂移信号由月度审计机制自己生产，主动澄清而非瞎猜
- 依赖：词典 + 漂移审计上线
- 成本：中

## C. 用户资产保管 vault（读写闭环，用户主提议）★★★

### C1. 存取闭环
- 场景：拖入 毕业论文.pdf "帮我存一下" → 镜子："已保存，记成「毕业论文」，分类：学习资料"→ 三天后"我之前存的那篇论文呢" → 吐出文件+当时的语境
- 独特性：网盘只是仓库，**这是"记得你为什么存它"的仓库**——文件过管道：AI 分类（contentType 枚举）+ embedding（之后能检索内容）+ 词典自动有实体指向
- "消化"：文档内容过 LLM 提摘要进 chunk，文件也被"读过"，问答能引用

### C2. 技术设计要点（讨论已定）
- 存储：文件落本地磁盘 `Mu-mirror-B/storage/vault/{userId}/`，库只存路径+元数据；**路径不进 git**
- 表：vault_items(user_id/文件名/存储路径/大小/mime/分类/LLM 摘要/chunk 关联/存入时间)
- 安全底线：上传走 JWT、下载校验 user_id、文件名清洗防路径穿越
- 确认红线：上传=显式动作免确认；**对话内"删掉/覆盖"必须确认**

### C3. 对话工具三件套
- save_item / find_item / recall_item 接进 toolcalling
- 论文叙事：**多模态记忆载体**——日记是快记忆，文件是重记忆，统一进检索+词典体系

## E. toolcalling 架构（已讨论待定稿）

### E1. 硬约束
- 工具执行权在 Java（Python 无状态不连库）；LLM 决策在 Python
- 用户 LLM 是任意 OpenAI 兼容 provider——**不是所有模型支持原生 tools API**，方案必须有退路
- 桩 LLM 不支持 tools API，全链路测试依赖不依赖它

### E2. 方案 A：Planner-Executor（推荐先行）
- 流程：提问 → B 调 Python 新 RPC PlanTools（LLM 按 JSON 约定输出"调哪个工具+参数"）→ B 执行（查库）→ 结果塞 ChatRequest.tool_results → 正常流式回答
- 一次额外 LLM 往返（几十 token）；任意模型能吃；流式不受影响；失败/超时/解析不出 → 跳过走现有 RAG（零回归）
- meta 事件带 tools_used → 前端展示工具轨迹

### E3. 方案 B：原生 function calling 循环（技术含量顶格，预留）
- Python chat_stream 带 tools → LLM 回 tool_call → Python gRPC 反调 Java ExecuteTool（Java 需起 gRPC server，调用方向反转）→ 结果回 → LLM 续写循环
- 代价：架构动刀 + 只对支持 tools API 的模型生效 + 桩 LLM 测不了
- **复用设计**：A 的工具注册表结构按 B 将来替换"决策来源"预留，执行层全复用

### E4. 论文三档消融实验（阶段 6 素材）
- 无工具 vs Planner-Executor vs 原生循环：检索命中率/回答质量/延迟三组数
- 加上词典开关消融（Hit@5/MRR）→ 实验章节两套现成素材

### E5. 工具审计表
- tool_calls(user_id/session_id/tool/args/result_summary/latency/created_at)
- 论文图表素材：工具使用频率/成功率/延迟分布

### E6. 前端配套
- 气泡上方"工具轨迹"芯片（"查了 9 月记录 · 12 条"），风格同 sources
- vault：输入栏附件按钮+拖拽上传、气泡内文件卡（图标+文件名+大小+下载）、"我的资产"入口
