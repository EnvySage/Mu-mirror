# 成就系统决策与维护约定

日期：2026-11-11。范围：34 枚蚀刻章、账号进度、解锁通知，以及 8 / 10 位展示架。

## 采用的方案

继续由 Java 后端管理业务事实，使用现有 PostgreSQL、Spring 事务与定时任务。规则从版本库中的 JSON 目录加载；数据库事务内写入事件队列，后台按用户重新核对统计值并授予成就。

对比过三种方案：

| 方案 | 维护成本 | 取舍 |
| --- | --- | --- |
| PostgreSQL 事务队列 + 共享统计项 + 配置规则 | 低；随现有后端和数据库部署 | 本次采用；业务提交和事件入队原子完成，进程重启后可继续消费 |
| 每枚章分别在业务代码中判断 | 起步低，后期重复多 | 每次改阈值都会碰业务流程，难以统一补发和去重 |
| 独立消息服务与规则引擎 | 高；增加基础设施、部署与排错成本 | 当前规模没有必要，暂不引入 |

不增加 Python 的职责，不依赖 AI 判断是否解锁。后续只有新的统计来源需要写代码；已有统计项上的阈值、组合条件、名称、星级、分类和章面通过目录维护。

## 数据与规则约定

- 唯一可编辑目录：`src/main/resources/achievements/catalog.json`。稳定的 `code` 是身份，不能用改名称的方式复用旧编号。
- 支持正整数阈值 `gte`、`all` 与 `any`，最多四层组合。启动时校验目录、规则及统计项名称，错误直接阻止启动。
- 已授予成就永久保留。删除来源、提高门槛、修改规则版本，都不撤销既有章。改门槛时递增 `ruleVersion`；本版没有重置、撤章和周期性重复领取。
- 星级只表示设计难度，由目录定义；与解锁统计分开。隐藏章解锁前，账号 API 隐去名称、图案、条件和进度。
- 当前状态统计从业务表读取；需要跨清理周期保留的成功对话、完成待办、模型验证、使用行为保存去重事实。日期统一使用 `Asia/Shanghai`。
- 用户身份来自服务端 JWT。客户端只能上报少数查看类动作，不能上报“成功对话”“模型测试通过”等服务端事实。
- 客户端查看动作验证资源归属及状态；这能证明资源可访问，不能证明用户认真阅读。资产检索打开动作目前由对话引用卡触发，服务端验证已归档资产，未持久化单次检索令牌。

## 扩展步骤

1. 新章沿用现有统计项：在目录增加定义和规则，放入前端章面，运行 `python scripts/sync-achievements.py --write`，再运行无参数检查。
2. 新统计项：在 `AchievementMetrics` 注册查询；需要保留历史时通过 `AchievementActivity` 写入去重事实。新业务表需要在新的迁移中接入事务事件。不要逐章复制 service 或创建计数表。
3. 新规则操作符：同时扩展规则校验、判断与进度返回，并补充行为测试。不要允许目录执行 SQL、SpEL 或任意脚本。
4. 发布后启动会安装新目录，并为旧用户排队核对。打开图鉴、读取待展示成就时也会核对，因此不依赖浏览器常开。

后端目录与前端预览数据、V16 与新库基线之间由同步脚本维护。生成文件不手工修改。正式登录环境始终从账号 API 读取；公开预览使用静态目录和本机展架，两种进度不混合。

升级操作、接口、统计口径和验证方式见 [achievements-operations.md](achievements-operations.md)。
