# 记录编辑与异步向量重建设计

**状态：待评审**

**日期：2026-10-17**

## 目标

记录文本编辑期间保留当前已生效的内容、记忆授权和向量。只有用户明确保存修改后，后端才提交新文本并使旧向量退出检索；用户撤销草稿或恢复原文时不产生后端写入。记忆授权后的向量重建在后台执行，页面及时返回，并能显示进度、失败和重试状态。

## 当前问题

- `ChunkCard.vue` 在文本框失焦时调用保存接口，因此每次临时离开编辑框都会把草稿提交给后端；界面没有明确的取消/恢复动作。
- `records` store 收到编辑成功后立即更新本地文本，并把 `ai_memory_approved` 与 `has_embedding` 置为 false。
- `ChunkServiceImpl.update()` 检测到文本变化后清空数据库向量、撤销记忆授权，并使引用该记录的镜子退出后续 AI 上下文。当前这发生在自动失焦保存时。
- `RecordServiceImpl.confirmReview()` 在同步请求中调用分类与 embedding gRPC；embedding 调用最多等待 30 秒，前端授权请求等待更久才显示结果。异常被记录后可能仍返回成功状态，用户无法可靠判断向量是否已就绪。

这导致“编辑草稿”和“提交新版本”混在一起，也导致向量工作受网络请求时长和进程重启影响。

## 设计决策

### 方案比较

1. **继续失焦自动保存，只延迟清向量。** 改动较小，但草稿仍会被意外提交；用户回到原文也无法恢复已经撤销的授权和向量，因此不采用。
2. **前端草稿加显式保存；提交后由数据库状态驱动后台 worker。** 旧向量在编辑期间保持有效；改变内容后事务性提交新文本、撤销旧授权/向量并记录后续状态；后台任务有持久化记录，服务重启后可以继续处理。选择此方案。
3. **前端草稿加消息队列。** 可扩展到多 worker，但当前项目没有既有队列基础设施，新增部署依赖和运维成本不适合本次需求，暂不采用。

## 用户可见行为

1. 输入时只改本地草稿，不发保存请求，也不改页面上已生效的记忆状态。
2. 提供明确的“保存修改”和“取消”操作。取消丢弃草稿；若草稿与原文相同，保存按钮不可用或保存被识别为空操作。两者均不触发授权撤销、镜子链失效或 embedding。
3. 保存不同文本时先显示正在保存。服务端事务成功后显示“修改已保存”；若该片段原本已授权，沿用现有安全规则撤销对旧文本的授权，清除旧向量，并要求用户重新授权。修改已保存与向量待生成是两个状态，不把“保存成功”误报成“已可检索”。
4. 用户重新授权后，接口快速返回“已加入重建队列”。卡片显示“向量重建中”；完成后显示“已可用于记忆”；失败时显示原因摘要与“重试”。失败不恢复旧向量，也不把新内容伪装成已就绪。
5. 页面切换或刷新后，重新读取后端状态仍显示相同任务进度。离开页面不会取消保存或后台任务。

## 后端状态与一致性

### 草稿与提交边界

- 文本输入组件保留 `originalSegment` 和 `draftSegment`。自动失焦保存改为仅校验/收起编辑态，不提交内容。
- 显式保存只提交实际变化的片段；批量编辑时只包含脏字段，避免无关元数据更新导致向量失效。
- 文本未变化时后端也做幂等检查，不撤销授权、不清除向量、不使镜子 lineage 失效。
- 文本变化提交成功时，仍在同一数据库事务内更新正文、撤销旧文本授权、清空不再匹配正文的向量，并调用现有 lineage 失效逻辑。此时旧向量不能留在新文本记录上，以免检索把新正文与旧语义混用。
- 回滚保存事务时，正文、授权、向量及 lineage 状态一并保持原样。用户取消未提交草稿没有任何数据库影响。

### 持久化 embedding 任务

- 为片段增加明确的 embedding 状态：`not_requested`、`pending`、`ready`、`failed`。`has_embedding` 可继续用于兼容，但不作为唯一状态依据。
- 新增持久任务表，记录 chunk、内容版本/哈希、状态、尝试次数、下次重试时间、最后错误摘要、租约/领取时间和时间戳。由授权事务在同一事务中写入 `pending` 任务，避免授权成功但任务丢失。
- 后台 worker 领取任务后在事务外调用 AI 服务。成功后只在 chunk 当前内容版本/哈希仍与任务相同时写入向量并标记 `ready`；若内容已再次变化或用户已撤权，丢弃过期结果，不覆盖当前状态。
- 临时错误采用有限次数的指数退避；超过上限标记 `failed`，保留可读错误和人工重试入口。服务启动时重新领取超时租约任务。
- 同一 chunk 同一内容版本最多有一个活动任务。重复授权请求、网络重试均幂等；取消授权会使未完成任务失效，迟到的 worker 结果必须丢弃。
- worker 失败只影响该 chunk 的 embedding 状态，不回滚用户已保存的文本，不恢复撤销的旧授权/向量，也不影响其他片段。

### 状态接口与前端刷新

- 编辑/授权 API 快速返回当前 chunk 与 embedding 状态；授权接口不等待 AI gRPC。
- chunk 查询响应携带 `embedding_status`、最近任务更新时间和必要的错误摘要。失败重试接口以 chunk 和当前内容版本为幂等边界。
- 前端在当前记录详情可见期间轻量轮询 pending 状态；离开页面停止轮询，但不停止服务端任务。轮询发现版本变化时更新状态；失败时停止高频轮询并展示重试。
- 如现有状态推送设施成熟，可后续换成 SSE/WebSocket；本次不引入新推送依赖。

## 迁移和兼容

- 数据迁移为已有向量设为 `ready`，没有向量的片段按授权状态映射到 `not_requested` 或待授权状态，不自动生成或删除任何向量。
- 新增任务表与字段采用向前兼容迁移；历史数据正文、授权值、向量和镜子快照不重算。
- 旧客户端即使继续调用保存接口，也由后端的内容比较保证相同文本不清空向量；前端发布后再移除失焦自动保存。
- 本设计只涵盖本地代码、迁移和本地验证，不包含生产服务器、生产数据库或部署操作。

## 验收标准

1. 输入后失焦不发写请求；取消草稿后数据库中的文本、授权、向量和镜子 lineage 均不变。
2. 草稿改动后恢复原文再保存，不清向量、不撤授权、不生成 embedding 任务。
3. 显式保存不同文本后，正文更新、旧授权/向量失效及 lineage 失效原子提交；事务失败时这些状态全部保持旧值。
4. 明确重新授权后，接口在不等待 embedding 的情况下返回 pending；后台完成后状态变为 ready，向量对应当前内容版本。
5. worker 遇到超时、进程重启、重复领取或内容再次编辑时，不丢任务、不写入过期向量；失败对用户可见并可重试。
6. 撤权后 pending 任务不能恢复授权或写入向量；其他片段的任务互不影响。
7. 已有数据库迁移后，存量向量与授权保持不变；不调用 AI 批量重建历史向量。
8. 前端刷新和跨页面后能读取真实状态；保存完成与 embedding ready 使用不同提示。
