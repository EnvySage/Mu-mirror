# Agent 按需检索与陪伴对话设计

> 状态：待用户审阅
> 日期：2026-10-16

## 目标

Mirror 应能自然回应问候、当下感受和日常分享，同时把回答范围留在个人回顾、日常整理与待办管理。Agent 自己决定是否需要读取个人记录；没有必要查记录时，直接进入对话。个人记录仍只允许使用已授权片段，未确认内容不能进入检索或回答上下文。

## 当前问题

当前 Java 流程先调用 `ExtractIntent`，再无条件进行四路 RAG 检索，之后才运行 Agent 工具循环。即使规划器按提示为闲聊返回空工具计划，Java 仍会在检索和工具均无结果时直接输出“这一问我没对上”的兜底文案。因此闲聊被误当成记忆查询。

现有 `search_records` 工具负责结构化 SQL 条件过滤和原文短词匹配，不包含语义向量检索。现有记录检索逻辑需要变成 Agent 可按需调用的只读工具，不能因为工具循环的输入没有 RAG 结果而移除语义记忆能力。

## 设计

### 对话编排

保留 Java 驱动的工具循环、Python 无状态规划、JSON 工具计划和 Java 执行工具的信任边界。每轮开始时，规划器拿到当前问题、受限的同会话历史和工具注册表；系统不预先查询日记或画像。规划提示词要把“尚未搜索”与“搜索过但没有命中”分开：首轮没有工具结果表示尚未查询，不能据此要求规划器补查，也不能当成没有记录。

规划器可选择直接结束工具规划，或调用一个或多个只读工具。Java 随后始终进入流式回答阶段：工具结果存在时据此回答；没有工具结果时，根据当前问题进行有边界的陪伴回应。空工具计划不再等同于“没有找到个人记录”。

规划提示词改为**按工具能力做判断**：是否调用工具取决于工具结果是否会实质改变回答。删除“某类问题必须按固定顺序调用某几个工具”的硬编码配方；保留示例作为参考，允许规划器结合问题、历史和已返回结果，自主选择零个、一个或多个工具，并在需要时继续下一步。闲聊不应为调用工具而调用工具。Python 继续只负责模型决策，不连数据库；Java 按用户身份执行白名单工具并负责授权、预算和审计。这样放开推理选择，同时不放开数据权限。

### 记录检索工具

将现有 `search_records` 定为 Agent 使用的统一个人记录检索工具，并扩展它的语义：规划器提供已结合上下文消歧的自然语言问题，工具执行侧再调用 `ExtractIntent` 和现有四路检索，选择 profile、structured、semantic 或 hybrid。显式日期、情绪和内容类型条件仍可作为工具参数传入。`ExtractIntent` 不再对每条闲聊预先运行，只在 Agent 决定查个人记录后调用。

`search_records` 的工具说明和参数规则需同步更新，避免继续要求模型把 `query` 当作逐字匹配短词。`get_stats`、`get_profile`、词典和 Vault 工具维持当前职责。检索结果需要携带足够的记录、相关度和来源信息，供回答引用并用于现有 `sources`、工具轨迹展示。语义检索仍使用现有相似度阈值与授权过滤。

### 回答边界与无结果处理

回答提示词区分以下情况：

- 用户问候、感谢或分享当下生活时，简短自然地回应，可追问一个与当前内容有关的问题。不得推断用户过去，也不得编造日记事实。
- 用户在当前消息里明确表达情绪时，可以直接回应这份当下情绪，不要求先查历史记录；不得推断用户没有表达的情绪或原因。
- 用户询问自己的历史、状态或待办时，只能依据本轮工具检索结果回答。明确检索到零结果时，说明没有找到并请用户补充时间或事件线索。
- 用户请求与 Mirror 定位无关的通用问答或任务时，简短、友善地说明 Mirror 更适合陪用户回顾自己和整理日常，再将话题引回用户本人。
- 工具规划或记录检索失败时，不把失败伪装成“没有记录”，也不编造历史内容。普通闲聊仍可正常回应；记忆问题应说明暂时无法核实。

回答模型应区分“本轮没有执行记录搜索”“记录搜索执行成功但零命中”和“记录搜索失败”：只有第二种情况可以说“没有找到相关记录”；其余情况应说明目前无法核实。

Java 后端继续按已认证的 `userId` 执行工具，并在查询处强制授权过滤。Agent 的计划不能扩大工具白名单或读取范围。未授权片段、画像中未授权信息和旧向量不得因本次改造进入上下文。

## SSE 与持久化

维持现有 SSE 事件契约和前端渲染方式。工具调用继续产生 `meta.tools_used`，回答仍产生 `delta`、`sources`、`done` 等事件。助手回复继续保存到当前会话历史；工具结果只按既有规则作为本轮回答上下文，不作为长期记忆写入。

## 失败与兼容

保留 Java 侧工具执行、审计、循环步数和耗时上限。规划器失败时不自动把所有问题降级成 RAG 检索；回答模型按上述边界处理。记忆检索失败时明确告知无法核实。回答流本身失败时保留现有“暂时无法回答”兜底。

保留 protobuf 工具计划和结果结构；扩展后的 `search_records` 继续通过 Java 注册表提供给 Python 规划器，不引入模型供应商原生 tools API。`has_retrieval` 现有含义不再用于首轮规划，实施时应移除其提示词依赖；若字段暂时保留，应标记弃用并避免继续表达“必须先有 RAG”。

## 验收标准

1. 用户说“今天天气不错”，Agent 不调用记录检索工具；回答模型自然回应，不出现“我没对上”的记忆兜底。
2. 用户问“我上周做了什么”，Agent 调用适合的个人记录工具；结果只包含当前用户已授权的内容，并保留来源引用。
3. 用户问语义性历史问题时，Agent 调用 `search_records`，仍能使用现有向量检索与相似度过滤。
4. 个人记忆查询确实没有匹配内容时，回答明确说明未找到并询问线索，不拿无关记录凑答案。
5. 用户要求编程或其他通用任务时，Mirror 温和说明自身范围并引回个人记录、状态或待办。
6. 规划器、工具或回答阶段失败时，不虚构个人历史；闲聊路径不因没有记录结果而被阻断。
7. SSE 事件契约、已确认片段检索限制和存量向量保持不变。

## 不在本次范围

- 不新增通用搜索、联网、代码执行或其他任意任务工具。
- 不修改数据库结构、不执行迁移、不重算现有向量。
- 不调整前端页面和 SSE 契约。
- 不改变日记授权、片段确认、待办授权等既有产品规则。
